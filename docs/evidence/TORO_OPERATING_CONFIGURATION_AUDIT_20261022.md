## Alternativas y configuración recomendada

| Opción | Ventaja | Límite / decisión |
|---|---|---|
| Híbrido: Gateway existente en Lightsail; Supabase y Vercel con sus responsabilidades; Codex local para desarrollo/recuperación | Aprovecha inversión e integración existentes, conserva continuidad sin depender del PC encendido y permite controlar el Chrome autorizado localmente. | Recomendada. Recuperar fuente/binding y verificar privilegios, versión, backups y capacidad. No garantiza disponibilidad sin operar/medir el host. |
| Todo en el PC local | Inspección directa de archivos/navegador y buen entorno de desarrollo. | Adecuado para trabajo y respaldo frío; no duplicar consumidor/escritor productivo ni depender de que el PC esté abierto para servicio continuo. |
| Sustituir ahora por otro stack de agentes/gateways/colas | Puede ser útil ante una necesidad futura demostrada. | No recomendado ahora: aumenta migración, costos y riesgo de perder estado/compatibilidad sin cerrar primero los gates actuales. |

Mantener un TORO lógico y su Control Plane, no un proceso privilegiado compartido con toda persona. Para confianza diferente se requieren fronteras verificadas: acceso limitado y aislamiento real, con el mismo modelo canónico. Si el Gateway actual no ofrece esa frontera, bloquear la ampliación y preparar una propuesta revisable, sin desplegar otro como remedio automático.

No se prescribe un tamaño de Lightsail ni un costo/modelo comercial sin métricas o acceso a la cuenta. Primero observar memoria/CPU, presión del navegador, cola, latencia, fallos y factura; limitar trabajo pesado local según el gate existente. Después elegir capacidad o modelo por resultado aceptado. Sin baseline, el beneficio sigue NO_MEDIDO.

## Investigación oficial que cambia las decisiones

1. [OpenClaw: trust model](https://docs.openclaw.ai/gateway/security/trust-model), leído este turno: un operador o equipo mutuamente confiable por Gateway; agentes/sesiones no garantizan aislamiento hostil. Herramientas de sesión/delegación pueden cruzar agentes según configuración. Esta es la razón para endurecer el gate de ingreso, no prueba de que la versión instalada tenga esos defaults.
2. [OpenClaw: security](https://docs.openclaw.ai/gateway/security), leído este turno: loopback en instalación normal, autenticación/admisión, auditoría y restricciones de mensajes entre proveedores/conversaciones; contenedores pueden tener otro bind. Validar versión y configuración efectiva antes de copiar comandos/keys o cambiar red.
3. [OpenClaw: WhatsApp](https://docs.openclaw.ai/channels/whatsapp), leído este turno: transporte vinculado WhatsApp Web/Baileys y plugin; no asumir WhatsApp Business Cloud API/Twilio. Admisión de grupos, remitentes y captura de cuenta tienen semánticas diferentes. Una clave wildcard de grupo puede ampliar admisión; no usarla como decoración de prompt.
4. [OpenAI: Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview), leído este turno: soporta entornos hosted/self-hosted y estado de sesión; no obliga a reemplazar el runtime existente. La página declara retención de sesión, residencia actualmente en EE. UU. y no elegibilidad ZDR de esa API aun con sandbox self-hosted. Antes de añadirla, validar acceso, propósito, retención/residencia y minimización de datos; no se crea una sesión ni una clave en esta unidad. No extrapolar estas condiciones a todos los productos OpenAI.
5. [Supabase changelog](https://supabase.com/changelog.md) y [retiro de ciphers TLS CBC](https://supabase.com/changelog/cbc-tls-ciphers-deprecated), leídos este turno: retiro en HTTP APIs a partir del 10/11/2026 como fecha más temprana; TLS1.3 no cambia y no aplica a conexiones Postgres directas/pooler/Management API. Verificar clientes del host, no afirmar incompatibilidad ni desactivar TLS.

Documentación pública actual no acredita qué versión está instalada en Lightsail. Resultados de búsqueda de forks OpenClaw se usaron únicamente para localizar documentación oficial; no como contrato de configuración.

## Prioridad y siguiente aceptación

1. Recuperar acceso local real y fuente original del único Gateway documentado; mantener Writer OFF y API Kross pagada pausada.
2. Revisar ejecución de funciones privilegiadas y protección de contraseñas/MFA con su propietario y soporte del plan. En [funciones anon](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable) y [authenticated](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), comprobar propósito, grants efectivos, argumentos, controles de identidad/ámbito y consumidores antes de ajustar permisos. Para [contraseñas filtradas](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection), verificar disponibilidad y aceptar flujos de alta/cambio/recuperación antes de declarar protección activa. No se amplía acceso ni se cambia Auth por SQL.
3. Verificar configuración del Portal y runtime interno mediante acceso autorizado. Publicar el SHA revisado solo tras aceptación positiva y negativa de identidad/roles/aislamiento/salida y rollback.
4. Probar un flujo WhatsApp interno con autorización específica de ese piloto: lectura de proyecto → una tarea canónica → reintento sin duplicado → recibo → misma tarea en Portal → reconexión/continuidad → revocación y negativas cruzadas. El binding actual no satisface el piloto; no usar huéspedes reales para plumbing ni crear grants para pasar QA.
5. Medir costo/resultado, errores, intervención, frescura y restauración; entonces ampliar capacidades o retirar duplicados. [Avisos de rendimiento](https://supabase.com/docs/guides/database/database-linter) no son una autorización para eliminar índices o reescribir RLS en masa.
