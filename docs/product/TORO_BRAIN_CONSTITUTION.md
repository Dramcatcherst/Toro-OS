# TORO Brain — Product Constitution

**Status:** CURRENT
**Approved:** 2026-09-22
**Scope:** Master product architecture, portfolio intelligence and operating principles

## 1. Product definition

TORO Brain is a continuously improving AI operating brain for people, businesses and portfolios.

It understands how each authorized scope actually works, builds a governed model of that scope, connects the systems and evidence that already exist, coordinates specialized intelligence, executes permitted work, verifies outcomes, learns from corrections and reduces complexity for humans.

TORO Brain is the master intelligence, operating and execution product. Its workflow, approval, automation and action capabilities operate inside the same product identity.

`TORO OS` is retained only as a technical legacy alias where existing keys, repository names or integrations still depend on it.

Dreamcatcher Hotel is the first real proving ground. It is not the boundary of the product.

## 2. Core doctrine

> **Deep inside. Simple outside.**

TORO Brain absorbs internal complexity so the human experience becomes simpler.

A working TORO Brain must know:

- who/what the active scope is;
- what is true;
- where truth lives;
- which data may cross scopes;
- who may see/change it;
- which system is authoritative;
- which actions are safe;
- which actions require approval;
- how results are verified;
- how failures recover;
- what the system learned.

## 3. Scope model

TORO Brain does not assume one user = one company = one project.

It supports a graph of:
- principals;
- portfolios;
- organizations;
- businesses;
- workspaces;
- properties/locations;
- projects/products;
- clients;
- partners/allies;
- suppliers/providers;
- assets;
- workers/agents.

Relationships determine visibility and permissions.

Examples:
- Mauricio may control Atrapasueños;
- Atrapasueños may operate multiple businesses;
- Dreamcatcher may contain several properties/products;
- Mauricio may also own unrelated projects;
- external client businesses remain isolated even when TORO Brain operates them.

## 4. Isolation doctrine

Every scope must have an explicit isolation mode.

- **private** — no cross-scope use without explicit permission.
- **portfolio** — owner-authorized aggregate/cross-business reasoning allowed.
- **shared_project** — only explicitly shared project data crosses.
- **client_isolated** — strong external-client isolation.
- **public_reference** — approved/public information may be reused broadly.

Defaults:
- personal = private;
- external client = client_isolated;
- owned business = isolated until portfolio crossing is explicitly allowed.

Cross-scope access is a policy decision, not an inference.

## 5. Identity doctrine

One human has one canonical TORO identity.

That person may have:
- personal context;
- multiple organization memberships;
- multiple roles;
- multiple projects;
- multiple tool connections.

Organization offboarding removes organization access without deleting personal TORO data.

No subsystem may create a parallel identity universe.

## 6. Knowledge and learning doctrine

TORO Brain separates:

### Scope knowledge
Private facts, history, policy and context belonging to one person/business/project.

### Reusable TORO skill
A generic workflow/pattern stripped of protected scope-specific data.

A useful pattern may be generalized.

Private business facts may not silently become reusable training material.

Promotion path:

`scope observation -> validated pattern -> abstract skill candidate -> review/test -> reusable TORO skill`

## 7. Build order — engine first

### Layer 0 — Identity, Constitution and Scope Graph
Product identity, portfolio graph, scopes, relationships, source authority and brand rules.

### Layer 1 — Truth Model
People, businesses, customers, suppliers, assets, projects, tasks, finance, rules, risks, decisions, knowledge, evidence and freshness.

### Layer 2 — Connector Fabric
Every connected system declares authority, scope, health, privacy, cost, owner and failure behavior.

### Layer 3 — Intelligence and Orchestration
TORO determines context, specialist capability, authority, verification, permission and next action.

### Layer 4 — Workflow and Execution
`Intent -> scope -> context -> authority -> risk -> permission -> action -> evidence -> verification -> log -> next action`

### Layer 5 — Governance, Security and Resilience
Identity, RLS, tenant isolation, approvals, secret management, audit, backups, recovery and rollback.

### Layer 6 — Continuous Learning and Improvement
`Observe -> detect -> propose -> validate -> approve if required -> update -> test -> measure -> retain/revert`

### Layer 7 — Human Experience
WhatsApp, Portal, reports, notifications and future surfaces expose the same governed brain.

### Layer 8 — Portfolio Intelligence
Authorized cross-scope comparisons, dependency detection, opportunities and owner-level optimization.

### Layer 9 — Commercial/Productization
Repeatable onboarding, billing, support, templates and portable skills after readiness gates pass.

## 8. Proactivity doctrine

TORO Brain should continuously detect:
- repeated manual work;
- missing/failing connectors;
- configuration drift;
- stale information;
- duplicated tools;
- cost leakage;
- revenue opportunities;
- unanswered handoffs;
- project dependency conflicts;
- unused capabilities;
- weak recovery/backup;
- risky permissions;
- potential safe automation.

It should propose improvements proactively.

Proactivity never overrides privacy, scope or approval boundaries.

## 9. System-audit doctrine

TORO Brain must be able to audit the systems it depends on.

For each system it should know:
- expected configuration;
- observed configuration;
- drift;
- current version/capabilities where relevant;
- health;
- security findings;
- permissions;
- isolation;
- backup/recovery;
- owner;
- last verification;
- next verification;
- recommended improvement.

This applies to OpenClaw, Supabase, GitHub, Vercel, Kross, Alegra, WeSpeak, Dropbox, Airtable, networks/devices and future tools.

A configured system is not a verified system.

Master product / visible brand:
- **TORO Brain**

Legacy technical alias:
- **TORO OS** — compatibility only; not a second product, brand or brain

Internal capabilities/subsystems:
- `TORO <Name>`

Examples:
- TORO Identity
- TORO People
- TORO Personal
- TORO Comms
- TORO Tools

Specialist personas:
- TORO TERE
- TORO RICO

- TORO SKY
- TORO SOBRESITO

Normal users experience one TORO Brain.

## 11. Dreamcatcher rule

Dreamcatcher is the first full proof environment.

It may contain hotel-specific workflows and models, but those cannot become hard-coded assumptions in the universal TORO Brain core.

External pilots remain blocked until the readiness gate passes.

## 12. User experience principle

A normal user should not need to understand:
- databases;
- agent topology;
- connector internals;
- prompt engineering;
- model routing;
- data schemas.

The ideal experience:

**Ask TORO. TORO understands the relevant scope. TORO works within permission. TORO shows what matters. TORO proves what happened.**

## 13. Future workforce horizon

Not a near-term implementation priority.

Long-term TORO Brain may help train and coordinate:
- humans;
- AI workers;
- software agents;
- robots/physical workers.

Training does not grant authority.

Future worker lifecycle:

`role -> knowledge/SOP -> training -> simulation -> evaluation -> explicit permission certification -> supervised work -> evidence -> improvement`

Owners:
- TORO People;
- TORO Knowledge;
- TORO Agents;
- TORO Governance.

## 14. Anti-patterns

Do not:
- create parallel brains;
- create duplicate identity systems;
- create duplicate task/message/approval engines;
- leak across client scopes;
- treat connection as integration;
- treat integration as automation;
- treat automation as verified execution;
- store everything merely because it may be useful later;
- create a subsystem when a feature/workflow fits an existing subsystem;
- build speculative future complexity before a real workflow needs it.

## 15. Product north star

TORO Brain wins when a growing portfolio becomes:
- more understandable;
- more measurable;
- more resilient;
- easier to operate;
- less dependent on human memory;
- faster at good decisions;
- safer at execution;
- more profitable;
- easier for people despite greater internal sophistication.

The system should become smarter every month while feeling simpler every month.
